# Architecture decisions

- [0001](0001-detach-a-metadata-only-cli-worker.md) *(superseded by 0003)* — **Detach a metadata-only CLI worker.** Claude's hook process strips content-bearing fields and detaches the Stacktrace CLI so `SessionEnd` survives non-interactive teardown; the CLI remains the sole owner of consent, state, locking, retries, and upload.
- [0002](0002-render-findings-in-a-bounded-synchronous-hook.md) *(superseded by 0003)* — **Detect and surface a stall from the transcript.** A synchronous `PostToolUseFailure` hook measures the trailing run of one identical failure in the transcript and reports it to the terminal and to Claude; stateless, CLI-free, and early enough to still matter.
- [0003](0003-deliver-findings-through-a-session-monitor.md) — **Deliver findings through a session monitor, not lifecycle hooks.** A session-lifetime monitor carries findings on a channel the host actually reads, so the detached worker and the synchronous stall detector are both retired; `SessionStart` contributes notification guidance only.
- [0004](0004-own-the-slack-bridge-in-the-cli.md) — **Own the Slack bridge in the CLI, publish findings from the daemon.** The daemon publishes eligible findings through the adapter's existing `publish` command, the CLI takes over the validation now in `scripts/slack.py`, and the plugin keeps the consent conversation and nothing beneath it; `stacktrace-slack-app` stays a separate optional tool.
- [0005](0005-ask-three-questions-and-render-the-notification.md) — **Ask three questions at onboarding, and render the notification rather than improvise it.** Onboarding asks what the user cares about, how they want to be notified, and hands Slack off to `stacktrace slack connect` for OAuth; every answer is recorded by the CLI, never by the plugin. The inline alert gains a fixed specification that prints severity and confidence as two labelled grades and drops glyph and colour under `NO_COLOR`, which `scripts/session_start.sh` resolves because the model cannot read the environment.
